# Kinesis streaming consumer and structured metadata filters for AgentCore Memory

Two features land here: a Kinesis-based streaming consumer that reacts to memory record lifecycle events, and a metadata filter system threaded through the recall, search, and auto-recall paths. Both integrate cleanly with existing patterns — the streaming consumer ties into the service lifecycle, and filters are exposed as a simplified `{key, operator, value}` schema that gets converted to the SDK's more verbose format before dispatch. The implementation correctly defaults both features to off, preserving backward compatibility.

**Watch for:** The Kinesis polling loop silently swallows all errors during `poll()` — including expired shard iterators — with no re-initialization path, meaning the consumer will stop receiving data without any visible signal (confirmed). The `as any` casts for metadata filters bypass SDK type safety and will break silently if the SDK's field names diverge from what's assumed (confirmed). No test coverage exists for either new feature (confirmed).

## High-level view

The streaming consumer is a Kinesis shard-polling loop with start/stop/pause/resume lifecycle. It initializes shard iterators at `LATEST` on start, polls every 5 seconds, and invalidates the stats cache on mutations. The error handling during polling is too permissive — a shard iterator expiration (which Kinesis enforces after 5 minutes of inactivity or under resharding) will silently drop the shard without recovery.

Metadata filters pass through three layers: tools expose a simplified `{key, operator, value}` triplet, `convertSimplifiedFilters` transforms these into the SDK's `MetadataFilter[]` shape with type inference on the value, and the client methods pass them to the SDK with `as any` casts because the current SDK types don't yet expose the full filter API. When the SDK adds proper types, the casts will mask type errors rather than surfacing them.

Neither feature has unit tests. The value-type inference logic in `inferFilterValue` and the streaming consumer's state transitions are both complex enough to warrant coverage before the code matures.

1. **Shard iterator expiration kills polling silently** — When a Kinesis shard iterator expires (5-minute inactivity or resharding), the empty catch in `poll()` discards the error and the shard is never re-initialized. 3. **`as any` casts mask SDK shape mismatches** — `retrieveMemoryRecords` casts `metadataFilters` via `as any` on `searchCriteria`, and `listMemoryRecords` builds the entire input as `Record<string, unknown>`. 4. **`inferFilterValue` misclassifies numeric strings** — Values like `"2026"` or `"404"` that happen to parse as numbers will be sent as `numberValue` even when the user intended a string match. 5. **No test coverage for either feature** — `convertSimplifiedFilters`, `inferFilterValue`, `MemoryStreamConsumer` lifecycle, and the streaming tool all lack tests. The type-inference edge cases in `inferFilterValue` are particularly risky without coverage.
6. **Consumer start failure after service start succeeds** — If `streamConsumer.start()` throws during the service's `start()` method, the error is caught and logged but the service reports as ready. The streaming tool will then report "not configured" even though a consumer object exists. Consider nullifying `streamConsumer` on failed start or exposing the error state through `getStatus()`.

## Kinesis consumer polling and shard lifecycle

The poll loop catches all exceptions per-shard and continues:

```typescript
} catch {
  // Graceful degradation on poll errors - continue with other shards
}
```

When a shard iterator expires (Kinesis expires them after 5 minutes without a `GetRecords` call, or when shards split/merge), `GetRecords` throws an `ExpiredIteratorException`. This catch discards that error. The shard remains in the map with a stale iterator that will keep failing on every subsequent poll — creating a permanent silent failure for that shard's data. The fix is to detect `ExpiredIteratorException` specifically and re-initialize the iterator for that shard.

There's also no backoff. If Kinesis throttles the consumer (common under high fan-out), the next poll fires 5 seconds later regardless, potentially sustaining the throttling condition. A simple exponential backoff with jitter on consecutive failures would prevent this.

## Filter type inference ambiguity

`inferFilterValue` auto-detects whether a string value is a number, a datetime, or a plain string:

```typescript
function inferFilterValue(value: string): MetadataFilterValue {
  const num = Number(value);
  if (!Number.isNaN(num) && value.trim() !== "") {
    return { numberValue: num };
  }
  if (/^\d{4}-\d{2}-\d{2}T/.test(value)) {
    return { dateTimeValue: value };
  }
  return { stringValue: value };
}
```

The heuristic fires `numberValue` for any parseable number, including values that are semantically strings (e.g., a metadata key storing a version string like `"2"`, or a priority level `"1"`). Since the operator doesn't gate the inference (an `EQUALS_TO` on a numeric-looking string still gets `numberValue`), the server-side filter will compare against the wrong type and silently return no matches.

The datetime regex only matches ISO 8601 with a `T` separator, which won't catch date-only values like `"2026-01-01"` that users might reasonably pass to an `AFTER` operator.

## SDK compatibility and `as any` usage

Two distinct `as any` patterns appear:

In `retrieveMemoryRecords`, the metadataFilters are spread into `searchCriteria` with a cast:
```typescript
...(options.metadataFilters && options.metadataFilters.length > 0
  ? { metadataFilters: options.metadataFilters as any }
  : {}),
```

In `listMemoryRecords`, the entire input is built as `Record<string, unknown>` and the command constructor is called with `as any`:
```typescript
const input: Record<string, unknown> = { ... };
const command = new ListMemoryRecordsCommand(input as any);
```

The SDK's `OperatorType` currently only has `EQUALS_TO`/`EXISTS`/`NOT_EXISTS`, and `ListMemoryRecordsInput` doesn't have a `metadataFilters` field yet. This means the code is targeting a future API shape. If the eventual SDK types differ (e.g., the field is named `filters` instead of `metadataFilters`, or nested differently), the code will silently send unsupported parameters that the API ignores, and users will get unfiltered results with no error.

## Streaming tool lifecycle gap

If `streamingEnabled` is true but `start()` fails, the consumer object still exists (it was created before `start()` was called), so the tool's null check passes but the consumer reports `isRunning: false`. Calls to `pause`/`resume` will be no-ops that don't surface the underlying start failure — the consumer silently sits in a stopped state with no indication of why.

## Test coverage gap

Untested code paths shipping in this diff:

- `convertSimplifiedFilters` with its type inference (numeric strings, date-only strings, empty strings)
- `MemoryStreamConsumer` state machine (start → poll → pause → resume → stop)
- The streaming tool's action dispatch and edge cases
- Auto-recall filter application in `before_prompt_build`

The `inferFilterValue` edge cases are particularly likely to surprise users since the function makes silent type decisions that affect query semantics.
